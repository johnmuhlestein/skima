# skima
skima is a command line tool for managing relational database schemas which are defined in a prescribed
structure for both the current state and changesets over time. skima is specifically tuned
for Postgresql databases and is intended as a tool that can be part of a deployment pipeline
to keep the underlying service database in sync by version

### Compiling skima
skima is written in go using features from 1.21 - you will need the 1.21.x runtime to compile/execute.

From the command line, make sure you are in the root skima directory
run `go install ./...` this does require that you have configured your GOPATH environment variable which you can verify `go env GOPATH`

### Project Structure (for development)
skima uses a project structure recommended by the [Cobra](https://github.com/spf13/cobra) project - which is the library that provides the CLI subcommand and flagging capability.
You can also use the very helpful [cobra-cli](https://github.com/spf13/cobra-cli) for adding new commands or do it manually following the existing patterns in the code

skima also uses [Viper](https://github.com/spf13/viper), which is a sister project to Cobra for managing configurations across default files, explicit files, command line flags and environment variables

skima also uses go modules for managing library dependencies

### Working with a manifest
Projects that describe a database schema should follow this simple structure:

```
|-- myschema
|   |-- deltas
|   |   |-- v1_0_1.json
|   |-- state
|   |   |-- sql
|   |   |   |-- pre
|   |   |   |   |-- myfunction.sql
|   |   |   |-- post
|   |   |   |   |-- dataload.sql
|   |   |-- documents-table.json
|   |   |-- projects-table.json
```
Database objects are described using JSON for example a file named `documents-table.json` could look like the following:
```json
{
  "name" : "documents",
  "columns" : [
    {
      "name" : "id",
      "datatype" : "uuid",
      "nullable" : false
    },
    {
      "name" : "document_type",
      "datatype" : "varchar",
      "nullable" : true
    },
    {
      "name" : "file_location",
      "datatype" : "varchar",
      "nullable" : true
    },
    {
      "name" : "upload_timestamp",
      "datatype" : "timestamp",
      "nullable" : false,
      "default" : "NOW()",
      "dfltfunc" : true
    },
    {
      "name" : "project_id",
      "datatype" : "uuid",
      "nullable" : false
    }
  ],
  "primary-key" : ["id"],
  "foreign-keys" : [
    {
      "name" : "doc_project_fk",
      "columns" : ["project_id"],
      "reference" :
        {
          "table" : "projects",
          "columns" : ["id"]
        },
      "deleterule" : "no action"
    }
  ],
  "constraints" : [
    {
      "name" : "documents_file_location_unq",
      "type" : "unique",
      "columns" : ["file_location"]
    },

      "name" : "documents_document_type_check",
      "type" : "check",
      "condition" : "document_type in('STRUCTURED','UNSTRUCTURED')"
    }
  ]
}
```
This definition includes columns, with both constraints and default values, a primary key and a foreign key to another table

skima knows how to read this file and apply the DDL whether as part of an initial load or as a reference from a changeset used to 
manage the database over time.

### State SQL Files

Inside the `state` directory, you have the option of writing SQL files/scripts for things from creating functions to loading data. Files in the `pre` directory are loaded prior to creating other 
database objects (tables and views in this case). This is ideal for things like functions, particularly trigger functions, so that they are available at the point in time the tables are created.
Additionally, there is a `post` directory that will execute after all other objects are created. This is ideal for things like loading data into tables needed to act as a bootstrap on creation.

A changeset `function` add delta (`{"object": "function", "action": "add", "name": "myfunction"}`) runs the function's sql file
from `state/sql/pre/myfunction.sql`, the same file a state build runs. For manifests written before this, `state/sql/myfunction.sql`
is used when there is no file in `pre`.

### Changesets

Changes over time are defined as changesets - files named with a version number in the `deltas` directory. The example below has 2 changes - identified as **_deltas_**, 
so a changeset consists of one or more changes and each change is identified as a delta.
```json
{
    "version" : "1.0.1",
    "description": "Adding a new table by reference",
    "deltas" : [
      {
        "object":"table",
        "action":"add",
        "name":"projects"
      },
      {
        "object":"fk",
        "action":"add",
        "name": "doc_project_fk",
        "reference": "documents"
      },
      {
        "object": "pk",
        "action": "add",
        "name": "projects_pk",
        "reference": "projects"
      },
      {
        "object": "index",
        "action": "drop",
        "name": "documents_name_idx"
      },
      {
        "object": "column",
        "action": "add",
        "name": "file_location",
        "reference": "documents"
      },
      {
        "object": "function",
        "action": "add",
        "name": "update_last_modified_at"
      }
    ]

}
```
A delta can make the following types of changes
* table - add, drop
* view - add, drop
* index - add, drop
* trigger - add, drop
* functions - add, drop
* primary key - add, drop
* foreign key - add, drop
* constraint - add, drop (valid for check and unique)
* column - add, drop, rename, alter

#### Transactions
Each changeset is applied in a single transaction - its deltas, pre/post hooks and SQL deltas either all take effect or none do.
If any of them fails, the whole changeset is rolled back, the schema stays at the previous version and the run is recorded with a
`rolled back` status. Fix the changeset and run `skima apply` again.

Errors that skima tolerates (for example dropping a foreign key that does not exist, or the `bypass` codes of a SQL delta) do not
abort the transaction - each statement runs in its own savepoint.

Some statements cannot run inside a transaction, such as `create index concurrently`. A changeset containing them can opt out of the
transaction - its deltas are then applied one at a time, and a failure part way through leaves the earlier deltas in place.
```json
{
  "version": "1.0.21",
  "description": "build an index without locking the table",
  "transaction": false,
  "deltas": [
    {
      "object": "script",
      "description": "concurrent index",
      "sql": ["create index concurrently if not exists documents_type_idx on documents (document_type)"]
    }
  ]
}
```

### State build transaction
The first `skima apply` against a schema builds it from the state files - pre SQL files, tables, foreign keys, views and post SQL
files. Like a changeset, the whole build runs in a single transaction: if anything fails, every object it created is rolled back,
the run is recorded with a `rolled back` status and `skima apply` exits 1. Fix the state files and run `skima apply` again to build
from a clean schema. Views are created in savepoints too, so a view that depends on a view created after it is simply retried
inside the transaction. `skima apply --sql` (pre SQL files only) runs in a transaction the same way.

State SQL files must not contain their own transaction control (`begin`/`commit`). If a state SQL file cannot run inside a
transaction, such as one with `create index concurrently`, turn the transaction off for the state build with the `state.transaction`
setting - each object is then created one at a time, and a failure part way through leaves the earlier objects in place.
```yaml
state:
  transaction: false
```
The same can be set with `skima apply --state-transaction=false` or the `SKM_STATE_TRANSACTION=false` environment variable.

### Semantic Versioning
The naming convention for delta files is to simply give a file name as a semantic version, but replacing periods (.) with underscores (_) and starting with a "v".
skima also understand pre release versioning similar to `v1_0_2-rc_1.json` - the important parts are that a pre-release version uses a dash (-) to separate it from the release
version, and that whatever text you use also includes a version number as an iterator so that `v1_0_2` **>** `v1_0_2-pre_3` **>** `v1_0_2-pre_1`. The text (such as "pre" or "rc") doesn't matter.

## Using skima
skima has commands for applying schema, inspecting a specific database for schema versioning and success/failure to apply objects/changes,
inspecting the manifest (where the schema/changes are defined) 

As a command line tool, skima has a built-in help system, at the top level you can simply type `skima help` to view the full
list of top level commands and at each sub command you can use `-h, --help` i.e. `skima [command] --help`

### Validating the manifest
Every manifest file is checked against a JSON schema for its kind - tables, views and changesets. Validation catches
misspelled or unknown properties (property names are case sensitive and lowercase, as documented below), missing required
properties, invalid values and invalid JSON, and reports where in the file each problem is:

```
skima manifest validate
INVALID  state/documents-table.json
         /columns/2: additional properties 'nullabel' not allowed
INVALID  deltas/v1_0_4.json
         /deltas/0/mods: set exactly one of datatype, nullable or default to true
```

* `skima manifest validate` checks every state and changeset file in the working directory, and flags JSON files in `state`
  that are not named `<name>-table.json` or `<name>-view.json` since skima ignores them
* `skima manifest validate <file>...` checks individual files - the kind comes from the file name, or use `--type table|view|changeset`
* `--output=json` gives machine readable results; the exit code is 1 when any file is invalid

Validation also checks the references between files:
* **State files** - a table or view's `name` matches its file name (deltas load `state/users-table.json` for table `users`),
  no column is defined twice, primary key, index, constraint and foreign key columns exist, and foreign keys reference tables
  that have a state file (schema-qualified tables like `audit.events` are skipped)
* **Changesets** - the file name is a version (`v1_0_2.json`, `v1_0_2-rc_1.json`) that no other changeset shares - only one
  of two changesets with the same version would ever be applied. Each delta's definition must be where applying it looks:
  a table/view add needs its state file, a column add or alter needs the column in the table's state file, an index,
  trigger, constraint, fk or pk add needs it in the referenced table's state file, a function add needs its sql file
  (see [State SQL Files](#state-sql-files)) and script deltas and hooks need their file in `deltas/scripts`. Without these
  checks the apply fails part way, or the delta generates no DDL and is silently skipped

Old changesets can legitimately reference definitions that were later removed from the state files - a column added in
`v1_0_3` and dropped in `v1_0_9` is no longer in the state file. So `skima manifest validate` reports reference problems in
changesets as warnings (the exit code stays 0), unless they are in changesets newer than `--since <version>`. In CI, pass the
deployed version to make problems in the changesets still to be applied errors:
```
skima manifest validate --since 1.4.2
INVALID  deltas/v1_4_3.json
         /deltas/0/name: table 'users' has no column 'nickname' in state/users-table.json
```

`skima apply` validates before it changes anything: the state files plus any changesets newer than the deployed version
(changesets read their definitions from the state files), with reference problems in those changesets as errors. If anything
is invalid, nothing is applied. Changesets that were
already applied are not checked, so an old file never blocks a deploy. Use `skima apply --skip-validation` to bypass the check.

The schemas live in [`pkg/manifest/schemas`](pkg/manifest/schemas). To get completion and inline errors in an editor that
supports JSON schema, add a `$schema` property to a manifest file:
```
{
  "$schema": "https://raw.githubusercontent.com/johnmuhlestein/skima/main/pkg/manifest/schemas/table.schema.json",
  "name": "documents",
  ...
}
```

## The nitty-gritty details
The sections below describes the deeper details of skima, including how apply history is managed, configuration, manifest schema definition and usage, 
basic commands and examples of a typical workflow

### History tables
skima records every apply run in two tables in the managed schema
* `skima_schema_history` - one row per run, with the schema version, apply type (state, changeset, baseline, sql), status and timestamps
* `skima_schema_statements` - one row per statement executed during a run, with its status and a description

The most recent run with a `success` (or `complete` for a baseline) status determines the currently deployed version. A changeset
that failed and was rolled back is recorded as `rolled back`, and the statements it had already run are marked `rolled back` too.

Only one `skima apply` runs against a schema at a time. Each apply takes a postgres advisory lock for the schema, so if two deploy jobs
start together the second waits for the first to finish, then applies only what is still missing.

The wait is bounded by `--lock-timeout` (default `5m`; `lock.timeout` in the config file, `SKM_LOCK_TIMEOUT` in the environment),
which takes a duration such as `30s` or `15m` - `0` waits indefinitely. If the lock is still held when the timeout runs out, the apply
exits with code 1 without changing anything, and reports which session holds the lock so a stuck apply can be found (skima's
connections show up in `pg_stat_activity` with the application name `skima`):
```
Another skima apply is running against schema app1 (held by pid 128: skima on 10.2.0.14, connected for 2s) - waiting up to 5m0s
ERROR: timed out after 5m0s waiting for the apply lock on schema app1 (held by pid 128: skima on 10.2.0.14, connected for 5m2s) - nothing was applied. Rerun once that apply finishes, or set a longer --lock-timeout
```

### Configuration
Configuration is managed across based on the idea of sane defaults and the ability to override based on how the values are set. The *Environment Variables* section above
stated to provide some ideas about how this works.

#### Configuration files
The default/lowest level configuration file is named .skima.yaml and is found in the home directory - `~/.skima.yaml` if you either do not have this file or want to override
the behavior defined in this file you can use a different configuration file by setting the `config` command line argument. This argument can be added at any level of the command line
`skima apply --config=/location/to/your/config.yaml`

A config file named with `--config` must exist and be readable, and a `.skima.yaml` that skima finds must be valid - otherwise
skima exits with an error rather than carrying on without it. Having no `.skima.yaml` at all is fine: configuration then comes from
flags and `SKM_` environment variables.

### Commands
Many commands also accept flags that override configuration, in these cases, passing in a flag value would override something set in the configuration, for example the 
`skima apply` command would accept something like `skima apply --dbusername=altusername`. The manifest location can be set for any command with `--workdir` (or `-w`)

### Environment Variables
Any value that can be set in the configuration file can also be set as an environment variable. This is most helpful in the case of passing in a database password.
skima will look for environment variables that begin with *SKM_*. Any configuration can be overridden. You use an underscore in the name of the environment variable
to separate the different levels of the configuration hierarchy - for example `dbconn.schema` is `SKM_DBCONN_SCHEMA` and `workdir` is `SKM_WORKDIR`

```yaml
workdir: ./myschema
dbconn:
  connstring: localhost
  port: 5432
  database: postgres
  username: tenant1
  password: mypassword
  schema: tenant1_schema
```

As an example, to avoid putting sensitive information such as the database password into the configuration file, a CI/CD system may choose
to set up an environment variable `export SKM_DBCONN_PASSWORD=mypassword`

* name - the name of the view
* columns - a list of strings that represent the column names
* sql - the select statement to create the view - there must be the same number of columns listed in the select as define in the columns attribute
```json
{

  "columns": ["column1","column2","column3"],
```

### Constraint definition
skima currently supports adding `check` and `unique` constraints via explicit definition in a state file. You'll notice in the definition there is a `type` attribute
which must be one of `check`,`unique`. If the type is `unique` you must set a `columns` attribute - there can be one or more columns identified. If the type is `check` you must set the `condition` attribute to the expression to be used by the check

```json
{
  "constraints": [
    {
      "name": "documents_file_location_unq",
      "type": "unique",
      "columns": [
        "file_location"
      ]
    },
    {
      "name": "documents_document_type_check",
      "type": "check",
      "condition": "document_type in('STRUCTURED','UNSTRUCTURED')"
    }
  ]
}
```
### add/drop constraint delta
```json
{
  "version": "1.0.1",
  "description": "Adding and dropping constraints",
  "deltas": [
    {
      "object": "constraint",
      "action": "add",
      "name": "documents_file_location_unq",
      "reference": "documents"
    },
    {
      "object": "constraint",
      "action": "drop",
      "name": "documents_document_type_check",
      "reference": "documents"
    }
  ]
}
```

### alter column delta
delta definitions to alter columns behave a little different than the "simple" deltas we've seen so far. You tell an alter column delta which part of the column you want to alter. Currently we support the following types of change

* alter data type - this must be an accepted type change allowed by the database
* alter default - you can set or drop the default value
* alter nullability - either set to NOT NULL or NULL

This is achieved by adding _mods_ information to the delta - indicating true/false one of the types of changes you would like to make. The delta goes back to the state definition of the column to determine the correct value
exactly one of `datatype`, `default` or `nullable` must be set to true - to make more than one kind of change to a column, use one delta per change

```json
{ 
    "version" : "1.0.2",
    "description": "alter hist statements columns",
    "deltas" : [
      {
        "object":"column",
        "action":"alter",
        "name":"description",
        "reference":"skima_schema_statements",
        "mods": {
          "datatype": true
        }
      },
      {
        "object":"column",
        "action":"alter",
        "name":"description",
        "reference":"skima_schema_statements",
        "mods": {
          "nullable": true
        }
      }
    ]
}

```

### override column delta
An override column delta is one where you explicitly pass in the column definition information instead of reading the column
definition from the state file. The scenario where you would do this is if, for example, you want to create a new column which is not
nullable in a table that already exists. Your state file will be defined with `nullable:false` but this will fail until the column has data
in it. You would essentially create a temporary state of the column (`nullable:true`) until you can add data, then alter the column to the defined state.

A full example is below - add the column with the explicit definition, add data to the new column, alter the column to the desired
definition from the state file.
```json
{
  "version" : "1.0.20",
  "description": "Term definition name normalization",
  "deltas" : [
    {
      "object": "column",
      "action": "add",
      "name": "normalized_name",
      "reference" : "term_definitions",
      "def" : {
        "name" : "normalized_name",
        "datatype" : "text",
        "nullable" : true
      }
    },
    {
      "object": "script",
      "description": "populate the new normalized_name column",
      "sql": [
        "update term_definitions set normalized_name = lower(regexp_replace(rtrim(ltrim(regexp_replace(name,'[^a-z\\d\\s]','','ig'))), '\\s+','-','g')) where normalized_name is null"
      ]
    },
    {
      "object": "column",
      "action": "alter",
      "name": "normalized_name",
      "reference": "term_definitions",
      "mods": {
        "nullable": true
      }
    }
  ]
}
```

### SQL deltas pre/post hooks
There are some special kinds of deltas and behaviors for executing DML sql statements. These are SQL Deltas - a delta designed to run 1 or more SQL DML statements
and there are pre and post hooks as a feature of any other delta which can also run SQL statements but are tied to the success of the encompassing statement

#### SQL Delta
Like all other deltas, a SQL delta has an `object` in this case identified by the value `script` 
it also takes 4 other attributes 

* `description` : Just that, a description of what the sql statement(s) are doing
* `script` : points to a sql file in the `deltas/scripts` working directory this attribute is mutually exclusive with `sql` attribute. In particular, these are meant to run complex scripting that is not easily expressed in a single sql statement, 
   this is not intended for DDL you expect to repeat when a database is generated - you would want to use a `function` or other similar object for that
* `sql` : an array of sql statements to execute - this attribute is mutually exclusive with `script` attribute
* `bypass` (optional- used with `sql` types only) : an array of error codes that could be returned that would still indicate that the statement(s) should be considered to have completed successfully (for idempotent behavior)
  * If excluded, the behavior is for any error to result in processing failure
  * For example (see below) 23505 indicates a unique constraint violation which is why we would use it on statements that execute an insert with generated primary keys

```json
{
  "version": "1.0.10",
  "description": "how to use sql deltas",
  "deltas": [
    {
      "object" : "script",
      "description" : "remove Lack of Liquidity from term_definitions",
      "sql": [
        "delete from term_definitions where name = 'Lack of Liquidity'"
      ]
    },
    {
      "object": "script",
      "description": "content_maps and term_groups for OTC-301605",
      "sql": [
        "insert into content_maps (id, name, description, project_id, solution_id, created_by, last_modified_by) select overlay(overlay(md5(random()::text || ':' || clock_timestamp()::text) placing '4' from 13) placing '8' from 17)::uuid, 'OTC-301605 (Unstructured)','OTC-301605 (Unstructured)', p.id, p.solution_id, 'system','system' from projects p where name = 'Trade Reconciliation - Equity Derivatives'",
        "insert into content_maps (id, name, description, project_id, solution_id, created_by, last_modified_by) select overlay(overlay(md5(random()::text || ':' || clock_timestamp()::text) placing '4' from 13) placing '8' from 17)::uuid, 'OTC-301605 (Structured)','OTC-301605 (Structured)', p.id, p.solution_id, 'system','system' from projects p where name = 'Trade Reconciliation - Equity Derivatives'",
        "insert into term_groups (id, name, type, project_id, description, created_by, last_modified_by, content_map_id) select overlay(overlay(md5(random()::text || ':' || clock_timestamp()::text) placing '4' from 13) placing '8' from 17)::uuid, cm.name, 'GROUP', cm.project_id, cm.name, 'system','system',cm.id from content_maps cm where cm.name = 'OTC-301605 (Unstructured)'",
        "insert into term_groups (id, name, type, project_id, description, created_by, last_modified_by, content_map_id) select overlay(overlay(md5(random()::text || ':' || clock_timestamp()::text) placing '4' from 13) placing '8' from 17)::uuid, cm.name, 'GROUP', cm.project_id, cm.name, 'system','system',cm.id from content_maps cm where cm.name = 'OTC-301605 (Structured)'"
      ],
      "bypass": [
        "23505"
      ]
    },
    {
      "object": "script",
      "description": "trigger function",
      "script": "complex_dml_scripting.sql"
    }
  ]
}
```
#### using a pre/post hook
Similar to the behavior of a SQL Delta, all other types of deltas allow you to define either/both a pre or post execution statement. 
The use case being - you want to set a column to NOT NULL which was previously nullable. When doing the alter column statement you could apply a pre hook to set all the current null values to a value so that the alter statement does not fail

For all deltas, except the SQL delta you now have optional attributes
* `pre` - executes before the delta. If it fails, the delta is not applied and the changeset stops
* `post` - executes after the delta has been applied successfully. If it fails, the changeset stops (the delta itself is not rolled back)

Each hook takes one of the following attributes
* `sql` : an array of statements to be executed in order
* `script` : the name of a sql file in the `deltas/scripts` working directory - the same location used by SQL deltas. The file can contain multiple statements, which is useful for logic that is awkward to express as individual statements

`sql` and `script` are mutually exclusive - if both are set, only `sql` is executed.

```json
{
  "version": "1.0.11",
  "description": "using a pre hook with a delta",
  "deltas": [
    {
      "object": "column",
      "action": "alter",
      "name": "data_type",
      "reference": "term_definitions",
      "mods": {
        "nullable": true
      },
      "pre": {
        "sql": [
          "update term_definitions set data_type = 'string' where data_type is null"
        ]
      }
    }
  ]
}
```
A hook can also point at a script file. In this example `deltas/scripts/backfill_priority.sql` runs after the column has been added
```
|-- myschema
|   |-- deltas
|   |   |-- scripts
|   |   |   |-- backfill_priority.sql
|   |   |-- v1_0_12.json
```
```json
{
  "version": "1.0.12",
  "description": "using a script post hook with a delta",
  "deltas": [
    {
      "object": "column",
      "action": "add",
      "name": "priority",
      "reference": "term_definitions",
      "post": {
        "script": "backfill_priority.sql"
      }
    }
  ]
}
```
Unlike the SQL delta, there are no bypass conditions for pre/post statements - any error fails the changeset.
